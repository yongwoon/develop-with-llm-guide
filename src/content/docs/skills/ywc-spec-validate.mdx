## 사용 case

### task 를 만들기 전 spec 점검

`docs/specification/` 을 다 쓴 뒤 task 로 나누기 전에 한 번 검토한다.

<Tabs syncKey="tool">
<TabItem label="Claude Code">
```text
/ywc-spec-validate --spec docs/specification/02-features.md
```
</TabItem>
<TabItem label="Codex">
```text
$ywc-spec-validate --spec docs/specification/02-features.md
```
</TabItem>
</Tabs>

**결과물**: 심각도별 지적 목록과 task 분해로 넘어가도 되는지에 대한 판정이 대화에 나온다. spec 파일은 고치지 않는다.

### 만든 task 와 spec 의 어긋남 확인

<Tabs syncKey="tool">
<TabItem label="Claude Code">
```text
/ywc-spec-validate --spec docs/specification/02-features.md --tasks tasks/
```
</TabItem>
<TabItem label="Codex">
```text
$ywc-spec-validate --spec docs/specification/02-features.md --tasks tasks/
```
</TabItem>
</Tabs>

**결과물**: 위 보고서에 더해, task 가 맡지 않은 요구사항과 spec 에 근거가 없는 task 가 함께 보고된다.

## 쓰지 말아야 할 때

- 지적이 나올 것을 알고 통과할 때까지 자동으로 고치고 싶다 → `ywc-spec-ready`
- 구현된 code 를 검토하고 싶다 → `ywc-impl-review`
- 제품·사업 관점의 검토가 필요하다 → `ywc-product-review`
- 아직 spec 이 없다 → `ywc-plan` 이나 `ywc-spec-writer` 로 먼저 쓴다
